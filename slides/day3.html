Virtual machines and containers

A virtual machine runs its own kernel on virtual hardware. A container is a group of ordinary processes on the host kernel, with an isolated view of the system.

Start with history. Unix chroot (1979) gave a process its own view of the filesystem. FreeBSD jails (2000) and Solaris Zones (2004) isolated more of the system. Linux gained the needed kernel features between 2002 and 2013, LXC (2008) combined them, and Docker (2013) made them easy to use with images and a simple command line. Consequences of sharing the kernel: a container starts in milliseconds because no operating system boots; images are small because they contain no kernel; and a kernel vulnerability affects every container on the host, which is why host patching still matters. On a Mac or Windows laptop, Docker Desktop runs a small Linux virtual machine, and the containers run inside it. On your lab machine they run on the Ubuntu kernel itself.

Docker creates a new set of namespaces for each container (namespaces(7), Linux manual pages).

A namespace wraps a global system resource so that processes inside it see their own copy. The mount namespace arrived first, in Linux 2.4.19 (2002). User namespaces were completed in Linux 3.8 (2013), and a time namespace was added in 5.6 (2020). A demonstration you can run on the lab machine: start a container and run "ps aux" inside it. You see only the container's processes, starting at PID 1. Run "ps aux" on the host and the same process appears with a different, higher PID. PID 1 has a special job: it receives signals such as SIGTERM when the container stops. A process that ignores SIGTERM is killed after a grace period, 10 seconds in Docker and 30 seconds in Kubernetes by default. Docker does not enable user namespace remapping by default, so root in a container is root on the host kernel. This is one reason the Dockerfile in Lab 07 switches to a non-root user.

Control groups limit what a process can use

  • A control group (cgroup) limits the CPU time, memory, disk I/O and number of processes of a group of processes.
  • The kernel also counts usage per cgroup. docker stats reads these counters.
  • When a container uses more memory than its limit, the kernel kills a process in it (OOM kill).
  • When a container reaches its CPU limit, the kernel slows it down (throttling). It keeps running.
docker run --memory 256m --cpus 0.5 flight-status:1.0.0

Kubernetes requests and limits, later today, are applied through the same cgroup settings.

Namespaces control what a process can see. Control groups control how much it can use. Engineers at Google developed cgroups (first called "process containers"), and they were merged into Linux 2.6.24 in January 2008. Ubuntu 24.04 uses cgroup version 2, the single unified hierarchy. The two failure modes matter for operations. Memory is not compressible: over the limit, the kernel's out-of-memory killer ends a process, and Docker or Kubernetes reports the container as OOMKilled with exit code 137. CPU is compressible: over the limit, the process waits for the next scheduling period, so requests become slower but nothing restarts. Slow responses with no restarts can be a sign of CPU throttling. Ask the class: if a Java or Python service has a memory leak, which of the two do you expect to see? (Restarts with OOMKilled.)

Images are stacks of read-only layers

Each Dockerfile instruction that changes files adds a read-only layer. OverlayFS stacks the layers into one filesystem and adds a writable layer for each container.

The four lower layers are the image. They are read-only, and each one is stored and transferred as a compressed archive identified by its SHA-256 digest. Two images built on the same base share the base layers on disk and in the registry, so the base is pulled only once. The top layer belongs to one running container. When the application changes a file that came from a lower layer, OverlayFS first copies the file up into the writable layer (copy-on-write). Deleting a file adds a marker that hides it; the bytes stay in the lower layer. This is why deleting a secret in a later Dockerfile step does not remove it from the image. Because the writable layer disappears with the container, anything that must survive a restart, such as database files, goes in a volume. In Lab 07 you will run "docker history" to see these layers and their sizes.

The Open Container Initiative was founded in 2015 to standardise these formats. Because of them, an image built with Docker on your lab machine runs on containerd in k3d, on Amazon EKS and on Amazon ECS.

The Open Container Initiative was founded in June 2015 under the Linux Foundation by Docker, CoreOS and other companies. Docker donated its image format and its runtime, runc. The image and runtime specifications reached version 1.0 in July 2017, and the distribution specification in 2021. Why it matters to United: the build tool and the run platform can change independently. A pipeline can build with Docker or with Kaniko, push to Amazon ECR, and the same image runs in EKS or ECS. Nothing in the image is specific to Docker. One detail students meet in Lab 07: "docker build" produces an image manifest that points to a configuration object and an ordered list of layer digests. The image digest is the hash of that manifest, which is the subject of the next slide.

Tags and digests

k3d-registry.localhost:5000/flight-status:1.4.0
k3d-registry.localhost:5000/flight-status@sha256:9b1e5c0d…
  • A tag is a name that points to an image. Anyone with push rights can point it at a different image.
  • A digest is the SHA-256 hash of the image manifest. It identifies one image and cannot change.
  • latest is the default tag name. It does not mean the newest image.
  • Deploy by digest, or by a tag that your pipeline never reuses.
Walk through the two references. The first is registry host, repository and tag. The second replaces the tag with the digest. The danger with tags: if a pipeline pushes "flight-status:1.4.0" twice with different content, two nodes can run two different programs under the same name, and a rollback to "1.4.0" may not return the code you tested. Amazon ECR has a repository setting called tag immutability that rejects a push to an existing tag. The Lab 09 pipeline tags each image with the commit SHA. A commit SHA names one version of the code, so the tag is never reused for different code. The push step prints the digest, so you can see which exact image went to dev and prod. Ask the class: what does "image: postgres" in a manifest resolve to? (postgres:latest on Docker Hub, which changes whenever a new release is published.)

Dockerfile practices

  • Start from a small, maintained base image, for example python:3.12-slim instead of python:3.12.
  • Copy the dependency list and install it before you copy the source code.
  • Run the process as a non-root user.
  • Keep the build context small with .dockerignore, and exclude .git, caches and local secrets.
  • Run one main process per container and write logs to standard output.
Each practice has a reason. A small base has fewer packages, so fewer vulnerabilities and a faster pull. The full python image is several times larger than the slim image; Lab 07 compares their scan results. Order matters because Docker reuses a cached layer only if that instruction and every instruction before it are unchanged. Copying all source code first means every code change reinstalls all dependencies. A non-root user limits the damage if the application is compromised. The build context is everything Docker sends to the builder. Without .dockerignore, a "COPY . ." can put your .git history or a local .env file with credentials into the image. One process per container lets the platform restart, scale and log each part separately. Writing logs to standard output is a Twelve-Factor practice (Wiggins, 2011); the platform collects them, for example into CloudWatch Logs on ECS.

A Dockerfile for a Python web service

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY flightstatus/ ./flightstatus/
RUN useradd --uid 10001 --no-create-home app
USER 10001
EXPOSE 8000
CMD ["uvicorn", "flightstatus.main:app", "--host", "0.0.0.0", "--port", "8000"]
  • Dependencies are installed before the code is copied, so a code change reuses the cached dependency layer.
  • The server runs as user 10001, which has no special rights on the host.
Read the file top to bottom with the class. FROM picks the base image. WORKDIR sets the directory for the following instructions. The first COPY brings in only requirements.txt, and RUN installs the packages; "--no-cache-dir" keeps pip's download cache out of the layer. The second COPY brings in the application package. useradd and USER switch to an unprivileged user for everything that runs afterwards, including the container's main process. EXPOSE documents the port. It does not publish it; "docker run -p" or a Kubernetes Service does that. CMD uses the JSON list form, so uvicorn runs as PID 1 and receives SIGTERM itself. The shell form would start a shell as PID 1 that may not pass the signal on. In Lab 07 you write this file yourself and then change one line of code to see which layers Docker rebuilds.

Software bills of materials and vulnerability scanning

  • A software bill of materials (SBOM) lists every package in an image, with its version. CycloneDX and SPDX are the common formats.
  • A scanner such as Trivy matches those packages against vulnerability databases.
  • Each finding has a severity. A pipeline can fail when it finds a CRITICAL vulnerability that has a fix.
  • New vulnerabilities are published every day, so an image that passed last month can fail today.
An SBOM is an ingredient list. It answers the question "do we run the vulnerable version of library X anywhere?" without rebuilding anything. US Executive Order 14028 (May 2021) made SBOMs a requirement for software sold to the federal government, and since then many companies expect them from suppliers. Trivy, from Aqua Security, reads the operating-system package database and the language dependency files in the image, then compares the versions with vulnerability records. It can also write the SBOM in CycloneDX or SPDX format. Two practical points for the lab. Fail on findings you can act on: "--ignore-unfixed" skips vulnerabilities that have no fixed version yet. Also rescan images that are already running, because the database changes after the image is built.

Signing and provenance

  • A signature shows who published an image and that it has not changed since.
  • Sigstore's cosign signs an image digest and stores the signature in the registry next to the image.
  • Provenance records how an image was built, including the source commit, the build system and the build steps.
  • SLSA Build levels 1 to 3 ask for provenance, then provenance signed by a hosted build platform, then a hardened build platform.
  • A cluster admission policy can refuse images that are not signed by a trusted key.
Scanning tells you what is inside an image. Signing tells you where it came from. Sigstore started in 2021 as a Linux Foundation project. With cosign, a pipeline signs the image digest, either with a key it holds or with a short-lived certificate tied to the pipeline's identity (keyless signing). The signature is stored in the same registry. SLSA, Supply-chain Levels for Software Artifacts, version 1.0 (2023), defines Build levels. Level 1: provenance exists. Level 2: the provenance is generated and signed by a hosted build platform. Level 3: the build platform prevents one build from tampering with another or with the signing material. We do not sign images in the labs, because the lab has no trusted key infrastructure. In a production pipeline the signing step comes right after the push, and an admission controller in EKS verifies the signature before a Pod starts.

Docker Compose describes a multi-container application

services:
  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://flights:flights@db:5432/flights
    depends_on:
      - db
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: flights
      POSTGRES_PASSWORD: flights
      POSTGRES_DB: flights

Compose creates one network for the project, and each service is reachable by its name. The API reaches the database at the host name db.

Compose started in 2013 as a tool called Fig, which Docker acquired in 2014. The file format is now the open Compose Specification, and Compose v2 runs as "docker compose". The file declares services, and optionally networks and volumes. "docker compose up" creates a network, starts the database container, then the API container, and gives each a DNS name equal to its service name. Point out what depends_on does and does not do: it controls start order, but by default it does not wait until Postgres accepts connections. Lab 07 adds a healthcheck so the API starts only when the database is ready. The password is in plain text here. That is acceptable for a file that only runs on a developer's machine. The next slides show how the same setting is handled in an ECS task definition.

Amazon ECS concepts

A task definition is a versioned JSON document. A task is one running copy of it, and a service keeps the desired number of tasks running.

Amazon ECS was announced in 2014. Four terms cover most of it. A task definition describes one or more containers: image, CPU and memory, ports, environment variables, secrets, health check and logging. Every change creates a new revision; you never edit a revision in place. A task is a running instance of a task definition revision. A service keeps a desired count of tasks running, replaces tasks that stop or fail their health check, registers them with a load balancer, and rolls out a new revision when you update it. A cluster is a logical group of services and tasks. With Fargate it contains no servers you manage. Map to Kubernetes for the class: a task definition is close to a Pod template, a task to a Pod, and a service to a Deployment plus a Service. We use that mapping again later today.

At United, containers run on Amazon ECS with Fargate.

AWS announced Fargate in 2017. It removes the instance layer: you do not patch, scale or log in to servers. The trade-offs follow from the table. You choose task CPU and memory from a fixed list of combinations, for example 0.25 vCPU with 0.5 to 2 GB of memory. You cannot run privileged containers or host-level agents. Each task has its own elastic network interface, so security groups apply per task. Billing is per second with a one-minute minimum, which suits services that scale up and down during the day. Ask anyone in the room who runs services on ECS today: do they choose task sizes themselves, or does the shared CDK library set them? This tells you which parts of the task definition your teams usually edit.

This is the table students fill in during Lab 07, so go through it row by row. The image and environment rows are direct copies. Ports differ because Fargate has no host port mapping: the container port is the task's port on its own network interface. The secrets row is the important change. In ECS the task definition holds only the ARN of a secret in AWS Secrets Manager or Systems Manager Parameter Store. ECS reads the value when the task starts, using the task execution role, and passes it as an environment variable. The value never appears in the task definition. Logging moves from "docker logs" to CloudWatch Logs through the awslogs driver. The last row: in ECS the database would not run as a second container in the task. It would be Amazon RDS, a separate managed service.

What changes when the task runs in AWS

  • Each Fargate task gets its own network interface and private IP address in a VPC subnet.
  • The task execution role lets ECS pull the image and read secrets. The task role is what the application uses to call AWS APIs.
  • An Application Load Balancer sends requests to healthy tasks. It replaces the port mapping on your machine.
  • The database is a managed service such as Amazon RDS.
  • Logs go to Amazon CloudWatch Logs.
The image stays the same. The surroundings change. The two roles are a common source of confusion. The task execution role is used by the ECS agent before your code runs: pulling from ECR, fetching secrets, creating the log stream. The task role is assumed by your application code at run time, for example to read from an S3 bucket. Keep them separate so the application cannot read secrets meant for other services. The load balancer checks each task's health and only sends traffic to healthy ones, which is the same idea as the Kubernetes readiness probe in the next lecture. At United, the shared CDK library usually creates these pieces, so an application team mostly supplies the image and the task settings.

From Borg to Kubernetes

Burns et al. (2016) describe what Google learned from Borg and Omega. Kubernetes adopted labels instead of numbered jobs, one IP address per Pod, and independent controllers that reconcile state.

Google ran Borg, its internal cluster manager, from about 2003. Omega, described in a 2013 paper, explored a more flexible scheduler design. Kubernetes was announced and open-sourced in June 2014, and version 1.0 shipped in July 2015, when the Cloud Native Computing Foundation was founded to host it. Amazon EKS became generally available in June 2018. Rancher released k3s, the small distribution that k3d runs in Docker, in 2019. The ACM Queue article "Borg, Omega, and Kubernetes" (2016) lists lessons from Borg. Three of them influenced the Kubernetes API: give every Pod its own IP address instead of sharing host ports, group objects with labels instead of numbering them, and split control into small controllers that each reconcile one kind of object. The article is about ten pages and is a good read after the course.

The declarative API and reconciliation loops

Every Kubernetes controller runs this loop. A deleted Pod comes back because the ReplicaSet controller sees two Pods where the spec asks for three, and creates one.

This slide connects Day 2 and Day 3. Terraform reconciles when you run "apply". Kubernetes reconciles all the time. You change the desired state by writing an object to the API server, for example with "kubectl apply". Controllers watch the API server, compare the desired state with what is running, and act to close the difference. Then they start again. Two consequences. First, Kubernetes repairs itself: a crashed Pod, a deleted Pod or a failed node all show up as a difference and get fixed. Second, manual changes to a running object are overwritten if they conflict with the spec held by the owner. Editing a Pod that a Deployment owns does not last. In Lab 08 you delete a Pod on purpose and watch a new one appear within seconds.

The control plane and the nodes

Every component talks to the API server, and only the API server uses the datastore. In k3d, one container (k3d-devops-server-0) runs the control plane and your Pods.

Go through the components. The API server validates and stores objects; it is the only component that reads and writes the datastore. etcd is the usual datastore; k3s uses an embedded SQLite database when there is a single server. The scheduler picks a node for each new Pod, based on resource requests and constraints. The controller manager runs the built-in controllers, such as the Deployment and ReplicaSet controllers from the previous slide. On each node, the kubelet watches the API server for Pods assigned to its node and asks the container runtime, containerd here, to start them. kube-proxy programs the network rules that make Services work. In Amazon EKS, AWS runs the control plane for you across several availability zones, and you see only the API endpoint. Your nodes are EC2 instances or Fargate.

Deployments, ReplicaSets and Pods

A Pod is one or more containers that share an IP address and volumes. A Deployment creates a new ReplicaSet for each new Pod template, scales the old one to zero and keeps it for rollback.

Build the picture from the bottom. A Pod is the smallest unit Kubernetes schedules. Its containers share one network namespace, so they reach each other on localhost, and they can share volumes. Most Pods have one main container. A ReplicaSet keeps a number of identical Pods running. You rarely create one yourself. A Deployment manages ReplicaSets. When you change the Pod template, for example the image tag, the Deployment creates a new ReplicaSet and moves Pods from the old one to the new one. The old ReplicaSet stays with zero Pods, up to ten revisions by default (revisionHistoryLimit), and "kubectl rollout undo" scales it back up. In Lab 08 you will see the ReplicaSet names change with each rollout: the suffix is a hash of the Pod template.

Services and Ingress

A Service gives a set of Pods one stable name and address, and sends traffic only to Pods that pass their readiness probe. An Ingress routes HTTP requests to Services by host name and path.

Pods come and go and get new IP addresses each time. A Service is the stable front: a fixed virtual IP and a DNS name, such as flight-status.flightops-dev.svc.cluster.local. It selects Pods by label, and its endpoint list holds only the Pods that are ready. An Ingress describes HTTP routing: requests for a host name and path go to a Service. An Ingress controller does the routing. k3s ships Traefik as its Ingress controller, and k3d publishes it on port 8080 of your lab machine. In Amazon EKS, the AWS Load Balancer Controller usually turns an Ingress into an Application Load Balancer, which is the same role the load balancer plays in front of ECS services. In Lab 08 you open the app in the browser through the Ingress and see the version change during a rollout.

Liveness, readiness and startup probes

ProbeQuestion it answersWhat happens when it fails
StartupHas the application finished starting?The other probes wait. After too many failures, the container restarts.
LivenessIs the process still able to work?The kubelet restarts the container.
ReadinessCan this Pod take requests now?The Pod is removed from the Service. It is not restarted.

The flight-status API answers liveness checks on /health and readiness checks on /ready, which also tests the database connection.

Probes are how Kubernetes learns about the application's health. The kubelet runs them on each node, usually as an HTTP GET. The difference between liveness and readiness matters. If the database is down, every Pod's readiness check fails and the Pods stop receiving traffic, which is correct. If the liveness check also tested the database, the kubelet would restart every Pod, which does not fix the database and adds load when it comes back. So a liveness check should only test the process itself. Readiness is also what makes rolling updates safe: a new Pod gets traffic only when it reports ready, and the rollout waits for it. In Lab 08 you deploy a version whose readiness check fails and see the rollout stop while the old Pods keep serving. The startup probe (stable since Kubernetes 1.20) protects slow-starting applications from being killed by the liveness probe.

Requests, limits and quality of service

  • A request is the amount the scheduler reserves on a node. A Pod only goes to a node with enough unreserved capacity.
  • A limit is the most a container may use. Over its memory limit it is killed. At its CPU limit it is throttled.
QoS classRuleUnder memory pressure on the node
GuaranteedEvery container has CPU and memory requests equal to its limitsEvicted last
BurstableAt least one request or limit, but not GuaranteedEvicted by how far use exceeds requests
BestEffortNo requests or limitsEvicted first
Requests and limits are the Kubernetes interface to the cgroups from this morning. Requests are for scheduling. The scheduler adds up the requests of the Pods on a node and places a new Pod only where its requests fit. A Pod with no requests can be placed anywhere, which is how nodes become overloaded. Limits are enforced by the kernel, with the same behaviour as in Docker: memory over the limit means OOMKilled, CPU at the limit means throttling. Kubernetes derives a quality-of-service class from these settings. When a node runs short of memory, the kubelet evicts Pods, starting with those that use the most beyond their requests; BestEffort Pods have no requests, so they go first. Yesterday's ResourceQuota in each namespace requires requests and limits on every container, so the Lab 08 manifests must set them.

A rolling update, step by step

Settings: 4 replicas, maxSurge 1, maxUnavailable 0. There are never fewer than 4 ready Pods or more than 5 Pods. The dashed Pod has started but is not ready yet.

Work through the example. maxSurge is how many Pods may exist above the desired count during the rollout. maxUnavailable is how many of the desired Pods may be not ready. With surge 1 and unavailable 0, Kubernetes adds one new Pod, waits for its readiness probe to pass, removes one old Pod, and repeats. Ask the class to work out the other common setting: 4 replicas with the defaults, 25 percent each. (maxSurge rounds up to 1 and maxUnavailable rounds down to 1, so Kubernetes can replace two Pods at a time and capacity can drop to 3.) What if the new version never becomes ready? The rollout stops at step 2, the old Pods keep serving, and after the progress deadline (600 seconds by default) the Deployment reports that the rollout failed. That is the failure you create in Lab 08.

Role-based access control

A Role allows verbs on resource types in one namespace, and a RoleBinding grants the Role to a user, group or ServiceAccount. RBAC rules only add permissions, so anything a Role does not list is refused.

This is the identity the Lab 09 pipeline uses, created as code in Lab 06. Everything in the Role is scoped to one namespace. ClusterRole and ClusterRoleBinding do the same for the whole cluster, for objects such as namespaces. Show how to test permissions without guessing: "kubectl auth can-i create deployments -n flightops-dev --as=system:serviceaccount:flightops-dev:deployer" answers yes. The same question for "create namespaces" answers no. Kubernetes RBAC has no deny rules. A request is allowed if any binding allows it. That makes it easy to reason about: to know what an identity can do, read the Roles bound to it. In Amazon EKS, IAM identities are mapped to Kubernetes users and groups through EKS access entries, and the same RBAC rules then apply.

Continuous delivery and continuous deployment

Continuous delivery keeps every change that passes the pipeline ready to release at any time (Humble and Farley, 2010). Continuous deployment releases each of those changes automatically.

The two terms are often mixed up. In continuous delivery, the software is always in a releasable state, and releasing is a business decision that takes one click. In continuous deployment, every change that passes all checks goes to production with no manual step. Timothy Fitz described continuous deployment at IMVU in 2009; Humble and Farley's book Continuous Delivery followed in 2010. Continuous deployment needs strong automated checks and fast rollback, because no person looks at the change before users do. Many regulated organisations practise continuous delivery with an approval before production. Lab 09 is close to continuous deployment: a merge to main deploys to prod if dev passed. The next slides cover what makes that safe.

Build once, promote the same artifact

The image that passed the checks in dev is the image that runs in prod. Settings that differ between environments come from the environment, as variables and Secrets (Wiggins, 2011).

Humble and Farley call this "only build your binaries once". If each environment gets its own build, the thing in production is not the thing you tested: a dependency may have changed between builds, or a build flag may differ. Promotion means deploying the same image digest to the next environment. Only configuration changes: database address, replica count, feature settings. The Twelve-Factor App calls this strict separation of config from code. In Lab 09 the ci pipeline builds the image once, tags it with the commit SHA, deploys it to the flightops-dev namespace and runs smoke tests. When you push a release tag, the promote pipeline checks that the image for that commit exists and deploys the same image to flightops-prod. Nothing is rebuilt. In the Harness platform, the same idea appears as one artifact on a service, deployed by stages that target different environments.

Approvals

  • An approval is a pipeline step that waits for a named person or group to confirm.
  • Use one where a person adds information the pipeline does not have, such as a change window or a business sign-off.
  • Every approval adds waiting time to the lead time for changes.
  • The Harness platform has Harness, Jira and ServiceNow approval steps, with timeouts.
  • Harness Open Source has no approval step. In Lab 09, a person promotes a release to prod by pushing a git tag.
Approvals are a control, and like any control they have a cost. Accelerate (Forsgren et al., 2018) found that approval by an external change board was associated with lower delivery performance and no improvement in stability, while peer review of each change, as in a pull request, worked well. So ask what a specific approval checks. If the answer is "a person looks at the same test results the pipeline already checked", automate the check instead. If the answer is "the release must wait for the end of a sales event", that is information only a person has. In Lab 09 the pull request review is the human check. The branch rule on main means a change reaches prod only after review and a green pipeline.

Rolling and blue-green deployments

A rolling deployment needs little extra capacity but runs two versions side by side for a while. Blue-green needs two full environments and rolls back by switching traffic back (Fowler, 2010).

A rolling deployment is what you did in Lab 08: replace instances a few at a time. It is the default for Kubernetes Deployments and ECS services. The cost is a period where both versions serve users, so the two versions must work with the same database schema and the same clients. Blue-green, as Fowler described it in 2010, keeps two complete environments. You deploy to the idle one, test it, then switch the router. Rollback is another switch, which takes seconds. The cost is double capacity during the release, and database changes still need care because both environments use the same data. The Harness platform supports rolling, blue-green and canary strategies for Kubernetes and for Amazon ECS. In the labs we use the Kubernetes rolling update, because it needs no extra tooling.

Canary releases

A canary release sends a small share of real traffic to the new version and compares it with the current version before sending more (Sato, 2014). With plain Kubernetes, the split follows the Pod count.

The name comes from the canary that miners took underground to detect gas. Danilo Sato described the technique on martinfowler.com in 2014. The canary is judged by the same measures users notice: error rate and response time, compared with the stable version over the same period. If it is as good or better, the share grows, for example 10, 50, then 100 percent. If it is worse, all traffic goes back to stable, and only a small share of users saw the problem. With plain Kubernetes, one canary Pod next to nine stable Pods behind the same Service gives roughly a 10 percent split. Precise percentages need an ingress controller, a service mesh, or a delivery tool. The Harness platform's canary strategy for Kubernetes and its Continuous Verification step automate the compare-and-decide part.

Feature flags separate deployment from release

if flags.is_enabled("new-departures-board", user):
    return new_departures_board(flights)
return departures_board(flights)
  • The new code is deployed to production, switched off.
  • Turning the flag on releases the feature to some users or to everyone, without a deployment.
  • Turning it off again is the fastest rollback for that feature.
  • Each flag needs an owner and a removal date. Old flags multiply the code paths you must test (Hodgson, 2017).
Deployment is a technical event: new code is running. Release is a business event: users can use a feature. Flags let you do them at different times. That allows trunk-based development from Day 1, because unfinished work can be merged to main while switched off. Pete Hodgson's article lists four kinds of toggles: release toggles for unfinished features, experiment toggles for A/B tests, ops toggles to switch off expensive features under load, and permission toggles for features some users pay for. The risk is debt. Every flag doubles the paths through that code, so release flags should be removed once the feature is fully on. Some teams add a test that fails when a flag is older than its removal date. Harness also sells a feature flag product, separate from its CI and CD modules; we do not use it in the course.

Automated verification and rollback

A smoke test calls the new version the way a user would: a health check, a version check, one real request. The Lab 09 smoke test checks the version through the ingress; a "Going further" task adds the other two. A step with when: failure() rolls back when any earlier step fails.

Verification answers the question "is the new version working for users?" right after the deployment, while the previous version is still one command away. The lab pipeline uses three checks in increasing order of value: the rollout finishes (all Pods ready), the health and version endpoints return the expected values through the Ingress, and one real API request returns flight data. In the Harness platform, the Verify step goes further: it compares metrics and logs of the new version with a baseline, using sources such as Prometheus, Datadog or CloudWatch, and can trigger the stage's rollback. Automated rollback depends on the earlier practices: immutable images, a previous ReplicaSet to return to, and database changes that the old version can still work with. Ask the class which of these would be hardest in their own systems.

Forsgren et al. (2018) found that teams with high delivery speed also had high stability. The same practices improved both.

We started the course on Day 1 with these four measures. Now each one maps to things you built. Two of them measure speed: how often you deploy and how long a commit takes to reach production. Two measure stability: how often a deployment causes a failure and how long it takes to recover. The research behind Accelerate found no trade-off between the two groups: the best performers were fast and stable at the same time, because small, automated, reversible changes are both quicker and safer. The 2024 DORA report also tracks a rework rate, the share of deployments that were unplanned fixes.
